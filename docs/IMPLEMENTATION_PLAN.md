# Implementation Plan — Entity Resolution Pipeline

## Scope and Guardrails

This is an implementation sequence for `SRS-BL-1.0` and the frozen design. It preserves the six retrieval families, adds the optional benchmark-gated `multilingual_name` family, preserves the feature groups, LightGBM primary model, entity-level validation, single-workstation batches, and exact output contract. Retrieval algorithms, limits, multilingual model, feature formulas, sampling ratios, model settings, threshold, batch sizes, storage formats, and GPU use remain validation-selected.

## A. Phased Implementation

| Phase | Objective, modules, flow, and acceptance criteria | Expected artifacts |
|---|---|---|
| 1. Setup and validation | **Objective:** establish a reproducible Windows-compatible project foundation and validate a small sample. **Proposed modules:** `src/config.py`, `src/io/ingest.py`, `src/validation/input_validation.py`, `src/logging.py`; environment/dependency specification. **Inputs → outputs:** configured official TSV paths → validation report and input fingerprints. **Depends on:** none. **Tasks:** relative-path config, UTF-8 TSV parsing, schema/ID/source/ground-truth checks, deterministic sample selection, structured logging. **Accept:** valid sample produces fingerprints; malformed encoding/header/ID fixtures fail clearly; optional malformed attributes are flagged rather than used as evidence. | Config snapshot; environment record; input-validation report; input fingerprints; sample manifest. |
| 2. Preprocess and target indexes | **Objective:** create train/test-consistent normalized views and reusable S2/S3 indexes. **Proposed modules:** `src/preprocess/normalize.py`, `src/preprocess/contracts.py`, `src/indexes/build.py`, `src/indexes/manifest.py`. **Inputs → outputs:** validated records → normalized partitions and compatible index manifests. **Depends on:** phase 1. **Tasks:** preserve raw decoded fields; implement configured normalization interfaces; partition deterministically; build/reuse versioned target indexes; reject incompatible reuse. **Accept:** raw values remain recoverable; equal config/input fingerprints reproduce index identity; changed preprocessing invalidates reuse. | Normalized sample partitions; preprocessing config; index manifests; target indexes. |
| 3. Candidate generation | **Objective:** produce the final scored candidate set with provenance. **Proposed modules:** existing six families plus optional `multilingual_name` in `src/core.py`; union/checkpoint/reporting remain shared. **Inputs → outputs:** S1 batches plus target indexes → deduplicated candidate partitions and per-batch reports. **Depends on:** phase 2. **Tasks:** execute the six baseline families and optionally the semantic multilingual family; preserve S2/S3 independence, union by S1/target ID, method evidence, open country handling, no ground-truth injection, and model/config lineage. **Accept:** fixtures prove disabled-baseline equivalence, multilingual method contract, S2/S3 retrieval, provenance, and compatibility invalidation. | Candidate partitions; candidate-generation manifests; pre/post-limit and exclusion-reason reports; baseline-vs-updated candidate-recall report. |
| 4. Feature extraction | **Objective:** convert candidates into one shared, versioned model matrix. **Proposed modules:** existing feature modules and schema contract. **Inputs → outputs:** candidates plus normalized records → partitioned feature rows and schema manifest. **Depends on:** phases 2–3. **Tasks:** retain baseline features and add the validated `multilingual_name_hit` provenance feature; do not add embedding similarity until ablation evidence exists; enforce fixed types/order. **Accept:** one feature row per candidate; pair lineage remains intact; train/inference parity fixture rejects schema mismatch. | Feature schema/version manifest; feature partitions; validation report. |
| 5. Training-data preparation | **Objective:** create leakage-safe labelled examples. **Proposed modules:** `src/training/split.py`, `labels.py`, `sampling.py`. **Inputs → outputs:** training candidates, ground truth, features → persisted entity-level split and labelled/sample partitions. **Depends on:** phases 3–4. **Tasks:** persist S1-level split; label generated pairs only; retain every generated positive; report candidate misses; implement training-only hard/ordinary negative selection as configured. **Accept:** no S1 crosses split; validation labels never enter training-only artifacts; every generated positive remains; sampling metadata is reproducible. | Split manifest; label/candidate-miss report; sampling manifest; training/validation feature partitions. |
| 6. LightGBM training and validation | **Objective:** train and evaluate the approved primary classifier on a small scale. **Proposed modules:** `src/model/lightgbm_train.py`, `evaluate.py`, `artifacts.py`. **Inputs → outputs:** labelled feature partitions → validation probabilities and experiment record. **Depends on:** phase 5. **Tasks:** load schema-bound data, train LightGBM binary classifier, record configuration/seeds/metrics/resources, retain predictions by pair. XGBoost/CatBoost remain optional controlled challengers only. **Accept:** model receives the exact schema, produces pair-linked probabilities, and experiment metadata is complete; no test data used. | Model checkpoint; validation predictions; experiment record; resource telemetry. |
| 7. Threshold and final model artifact | **Objective:** select the official-metric decision policy and create a reproducible model bundle. **Proposed modules:** `src/model/threshold.py`, `src/model/manifest.py`. **Inputs → outputs:** validation predictions → threshold-sweep report and selected model manifest. **Depends on:** phase 6. **Tasks:** compute macro F0.5 per S1 including singletons, assess threshold stability, freeze selected config and threshold, then retrain on eligible training data. **Accept:** chosen threshold is supported by validation record; model, schema, preprocessing, candidate config, split and threshold hashes are bound in one manifest. | Threshold sweep/stability report; final model; model manifest. |
| 8. Batch inference and outputs | **Objective:** execute the exact test-time pipeline and generate both TSVs. **Proposed modules:** `src/inference/run.py`, `score.py`, `output_writer.py`, `output_validation.py`. **Inputs → outputs:** test TSVs plus compatible model bundle → staged `matching_results.tsv` and `candidate_pairs.tsv`. **Depends on:** phases 2–4 and 7. **Tasks:** validate compatibility before processing; batch candidates/features/scores; apply threshold without one-to-one restriction; retain original S1 order; atomically promote validated output. **Accept:** one row per test S1; permitted unique S2/S3 lists; empty-list serialization; every match is in the scored candidate set; official validator runs when available. | Test index/candidate/feature/score partitions; staged and validated output TSVs; inference manifest. |
| 9. End-to-end validation and benchmarking | **Objective:** prove recovery behavior and collect evidence for operating choices. **Proposed modules:** `src/operations/preflight.py`, `resource_monitor.py`, `checkpoint.py`; test fixtures. **Inputs → outputs:** representative partitions → benchmark, preflight, and recovery reports. **Depends on:** phases 1–8. **Tasks:** estimate peak disk space from artifacts; recheck usable SSD; measure RAM/VRAM/runtime; verify Windows/library/GPU compatibility; test interruption/resume/corruption paths. **Accept:** no unsupported resource assumptions; only compatible checkpoints are reused; evidence supports or blocks full-scale configuration selection. | Storage preflight; benchmark report; compatibility report; checkpoint/recovery test record. |
| 10. Full scale and submission preparation | **Objective:** run the approved configuration, validate deliverables, and assemble the final package. **Proposed modules:** `src/operations/orchestrate.py`, `src/submission/package_check.py`. **Inputs → outputs:** selected manifests and full official data → final outputs and package-completeness manifest. **Depends on:** phase 9 decision. **Tasks:** run deterministic batches with checkpoints; monitor resources; validate both outputs; assemble official code/README/dependency/methodology structure. **Accept:** all batches complete or validly resumed; output contract and package completeness pass; all final artifacts are version-linked. | Full-run manifests; final TSVs; submission package manifest; methodology document/template completion record. |

## B. Milestones

| Milestone | Exit condition |
|---|---|
| Milestone 1 | Project setup and data validation succeed on a deterministic small sample. |
| Milestone 2 | All six retrieval families and six feature groups run end to end on sample data with provenance and schema checks. |
| Milestone 3 | A small-scale LightGBM model trains, validates, and produces pair-linked predictions. |
| Milestone 4 | The complete pipeline generates both required TSVs and passes output contract checks. |
| Milestone 5 | Storage/RAM/runtime/compatibility measurements support a full-scale execution decision. |
| Milestone 6 | Full-scale outputs and final submission package are validated. |

## C. Dependencies, Risks, and Decision Gates

| Risk or dependency | Required gate / mitigation |
|---|---|
| Windows, Python, LightGBM, ANN, CUDA, and driver compatibility | Verify in phase 1 and again before GPU-enabled workloads; retain CPU fallback only where the selected method supports it. |
| 128 GB RAM and approximately 336 GB observed free SSD | Recheck actual work-volume space; estimate peak artifacts before full scale; stream/partition and checkpoint. |
| Candidate recall versus explosion | Compare each method and union using candidate recall, volume, reduction ratio, incremental positives, and resource use; do not impose an arbitrary global cap. |
| Embedding/ANN resource and license requirements | Select only after compatibility, license, index-size, and retrieval-value evidence; preserve the method family even while implementation is selected. |
| Training size and negative sampling | Keep all generated positives; restrict hard-negative mining to training partition; benchmark sampling configuration without leakage. |
| Runtime, interruption, and corrupted artifacts | Use deterministic batch IDs, atomic writes, checksums/manifests, and recovery tests before full scale. |
| Open parameters | Decide only through controlled validation/benchmark records: normalization, retrieval settings, feature formulas, sampling, hyperparameters, threshold, workers, storage format, and GPU use. |

## D. Exact Implementation Sequence

1. Build phase-1 configuration, logging, ingestion, and validation fixtures first.
2. Implement normalized-record contracts and target-index manifests; these gate all retrieval work.
3. Implement candidate union/provenance/reporting alongside the six retrieval adapters; the adapters may be developed independently once the shared contract exists.
4. Implement feature-schema enforcement, then the six feature-group modules independently against the shared pair contract.
5. Add split, labels, candidate-miss reporting, and sampling only after candidates/features are stable.
6. Add LightGBM training, evaluation, and threshold selection in that order; model alternatives wait for a stable LightGBM baseline.
7. Build inference by reusing preprocessing, candidate, and feature modules rather than duplicating logic; then implement output writer/validator.
8. Add preflight, telemetry, checkpoint/resume, and failure-path tests before any full-scale run.
9. Proceed to full scale only after the phase-9 evidence supports the selected configuration; package assembly is the final step.

Independent work is limited to retrieval adapters after their common interface exists, feature-group modules after schema definition, and test fixtures/documentation alongside their owning phase. Training depends on completed candidate and feature contracts; inference depends on the selected model manifest; full-scale execution waits for resource evidence.
